# 简单表格底色与局部自动文字色

## 两个独立属性

正文顶层无合并、无嵌套的矩形表格，逐格支持：

- `cellFillRgb`：六位大写 RGB，不含 `#`；省略恢复既有默认底色，表头仍使用原有浅蓝底色
- `cellTextColorMode: "auto"`：局部自动文字色；省略使用原有 profile / 显式文字颜色

两项独立保存、重置。重置底色不移除自动文字色；重置文字模式不移除底色。自动模式也可用于没有显式底色的单元格。`null` 仅为编辑器内部缺省，不是合法持久模型。缺省 V1 / V2 模型的全包编码保持历史字节，未改变全局 `docDefaults`、Normal 或样式 profile。

工具栏提供底色色盘、RGB 输入与应用、默认底色，以及独立的“默认 / 自动”文字模式。文本输入接受可选 `#` 及小写并规范化为大写；模型仍严格校验规范形式。操作沿用当前单元格 / 多格 / 行列 / 整表及文本范围选区规则，分别显示混合与默认状态。候选整体检查通过才提交，一次撤销；锁定、过期选区及迟到色盘事件不能修改新文档。新增行格从默认开始，结构删除和表头转换保留存活格的已设属性。

## 导出语义与预览边界

显式底色导出为直接 `tcPr/shd`：`val="clear"`、`color="auto"`、`fill="RGB"`。其中 `shd` 的 `color="auto"` 是图案前景，不能据此推断文字自动色。

局部自动文字模式仅为本格普通、没有显式 `textColor` mark 的文字 run 写入 `w:color w:val="auto"`。显式黑色和其他 RGB 优先。链接继续使用既有显式 / 默认链接色，不强改为自动色。没有设置自动模式的填色格继续使用既有默认文字色。没有把白色写进源模型或依据底色生成持久文字 RGB。

自动前景由 DOCX 消费者决定。编辑器与应用打印快照使用按底色相对亮度选择黑 / 白的**有限预览近似**，提示明确说明不等同于 Word / LibreOffice 自动对比算法；显式 RGB 与链接外观仍优先。它只存在于 DOM / CSS，不进入文档模型、草稿或 DOCX。尤其真实样本的橙底 `E97132`：LibreOffice 自动文字为白色，当前亮度近似可显示黑色，不能把浏览器预览当作源颜色证据，也不承诺两种输出像素相同。

实际浏览器 / WebView2 色盘、剪贴板、选区和原生打印尚未验收。无 DOM 的真实事务 / 控件回调，以及 LibreOffice 的 DOCX 渲染，是不同层次的证据。

## 外部 DOCX 导入证明

导入从同一有界源包快照分别证明底色与文字色。实际 OPC 关系定位主文档、样式与主题，不依赖 `word/theme/theme1.xml` 等约定名称。严格检查直接 `document/body/tbl/tr/tc/tcPr/shd` 路径、命名空间、属性身份、重复 / 包装声明、完整表行格形状及每段文字顺序。IR 的背景 RGB 只作交叉核验；vendor 会把图案混合成近似色，也会丢失主题元数据，不能作为底色来源。

首次支持直接 `clear` + 六位 RGB。另允许不带 tint / shade 等转换的 `themeFill="accent1"` 至 `accent6`，但实际唯一主题槽须是单一未转换 `srgbClr`，且与源 fallback RGB 完全一致。导出明确转换为固定 RGB，并提示动态主题联动不再保留。其他主题槽、缺失 / 外部 / 多义关系、不同 fallback、图案、表 / 行底色、活动样式或条件底色、复杂结构，不假定为受支持的直接填色。

活动表格样式按显式引用或实际缺省样式，以及唯一有界 `basedOn` 链解析；未使用模板声明不会导致新的普遍拒绝。直接 RGB 底色可以成立而自动文字证明失败，两者不会相互冒充。

自动色另解析相关 `docDefaults`、活动段落 / 字符样式链及直接 run 颜色，先证明每段有效色，再与转换后的逐字符文字和显式 RGB 核对。源码确实没有颜色或明确为自动，与 profile 的显式黑色是不同事实。只有已保留填色格中有实际文字的普通段落 / 直接文字 run 进入本轮自动色源子集，不从空格子的缺省值推断未来输入格式；混合的显式黑色 / 绿色仍保留。表格样式前景、默认字符样式前景、主题 / 条件 / 模糊颜色、段落或 run 底纹 / 高亮、链接、列表、标题及复杂内容，不能由 `IR color=None` 推成自动色。

未证明路径保留既有有警告的规范化，不笼统拒绝旧模板。颜色 IR 绑定或最终模型绑定失败时，整次新颜色附加原子取消并提示，避免列表转换或后部单元格身份变化导致新拒绝或部分误附加。原有其他审计的拒绝仍生效。旧广义主题 / 自动色清单警告可能包含未使用样式；本轮新增提示单独说明实际已证明的局部能力，不表示全文格式恢复。

自有 DOCX 重开必须使用完整哈希、部件集合及模型重编码一致性检查；普通 `import-docx` 不是可信模型重开。移除底色但保留自动模式的自有文档，可通过可信重开准确恢复；普通外部导入并不扩大为任意无底色自动文字支持。

## 真实原件和独立消费者

未改造 Apache POI `table-alignment.docx`：来源 revision `ae62bb5116b9aee19ebd5834e3a82066132c9f7f`，来源记录在 `scripts/table-position-corpus.json`；SHA-256 `ee36729e0d050e529fea0b444006a194bea72b35cf8958ae58c6624c26156b41`，15,519 字节。其 18 个橙底格都有直接 `clear` / `E97132` / `themeFill=accent2`，实际主题也为 `E97132`。活动 `TableGrid → TableNormal` 和相关文字默认 / 样式没有白色 RGB；消费者显示的白字是真正自动前景。

此前独立十文件实验区分填色、段落标记自动色、局部段落样式自动色及直接 run 自动色，证明仅填色或段落标记自动色仍为黑字，局部样式 / run 自动色才恢复白字。原件只移除 `themeFill`、保留正确 RGB 后，消费者坐标和像素不变。那些实验是独立消费者派生件，不是产品可信模型验收。

产品验证使用 `scripts/check-table-cell-colors.py`，独立 Python / OOXML 读取源、导出及实际编辑参考；实际候选事务与 undo / redo / 独立重置由 `tests/ui/edit-table-cell-colors.mjs` 驱动。每份 LibreOffice PDF 使用单独新 profile 与进程，不复用曾产生不稳定结果的批量 profile。另由 `scripts/check-table-cell-color-geometry.py` 对同一批已哈希 PDF 重测填色矩形边缘、文字原点及页码 / 字体 / 字号，不重复计作新渲染。结果计数、冻结身份、文件安全与全量旧路径重放见 [REGRESSION.md](REGRESSION.md)。

本轮颜色和纵向证据不消除已有横向列宽规范化：真实原件与产品输出的最大横向文字坐标差仍约 **145.85 pt**。不能声称整页、自动列宽、边框、字体替代、分页或 Word / WPS 全面相等。
